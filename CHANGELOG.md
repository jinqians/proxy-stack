# Changelog

All notable user-facing changes should be recorded here.

## Unreleased

- The Snell and Shadowsocks Rust installers come from the repositories' new names, `jinqians/snell` and `jinqians/ss-2022` (formerly `snell.sh` and `ss-2022.sh`).
- Uninstalling Snell (`psm standalone remove snell`, or the Snell menu) now removes everything the upstream snell.sh may have added, as snell.sh's own uninstall does. That is the binary of each channel (`snell-server-v4/v5/v6`) and its backups, the per-user services (`snell-<port>`), the ShadowTLS services in front of them, the rule-based routing (`snell-router`, with its own sing-box, nftables table and policy route) and the egress control (network namespace, veth pair, NAT). The ports those services listened on are closed in the firewall. Before, they were all left behind, and the per-user services kept running without their config.
- Relays grow up: `psm relay` gains **gost** (v3.3) beside realm, **tunnels**, **several landing servers**, **limits** and **ports picked for you**, and the PSM panel manages all of it. A forward runs on realm (the default) or gost; a tunnel is two rules with one name — `--mode tunnel-exit` on the machine that forwards to the landing side, `--mode tunnel-entry` where clients connect — carrying the traffic, UDP included, in gost's relay protocol over `--transport tls|mtls|wss|mwss` with a password. The exit makes a self-signed certificate and prints the entry's command; the entry pins it (`--exit-pin` / `--exit-cert`) and accepts no other, and the exit forwards to its own targets only, so it is no open proxy. `--target` can be given up to 16 times, shared by `--strategy round|hash` (either program) or `rand|fifo` (gost, failover with a TCP health check of each target every 15 s; `--no-probe` for a UDP-only target). `--speed` limits the rate (gost); `--limit-gb`/`--reset-day` meter the listening port on the `PSM_TRF` chain the nodes use and refuse new connections past the month's quota, `--expires` from a date on (both programs). `--listen-port auto` picks a free port in `--port-range` (20000-60000 by default), `--batch FILE|-` makes one relay per line, and `update` can move a rule between realm and gost on its port. gost runs as its own `psm-gost` service, so a gost you installed yourself is left alone. Measured on gost 3.3.0: a UDP listener needs keepAlive or every datagram leaves from a new source port (QUIC cannot hold a connection), and the relay connector's `nodelay` loses what the client sends next on every transport — it is left off, so a tunnel carries protocols in which the client speaks first (every proxy protocol) and not SSH, SMTP or FTP, which need a forward. `psm relay probe` reports each target's health, `psm doctor` checks every relay's port, migration carries `/etc/psm-gost`, and uninstalling asks about gost too. The menu keeps managing realm forwards and refuses to edit a gost rule (use `psm relay` or the panel).
- `psm sni check --input -`: the TLS handshake check of `psm sni find` alone, for candidates given on stdin. The PSM panel now asks the mapping engine itself and sends only the names it found, so the engine's API key never reaches a server.
- psm-agent 0.11.0: the relay tasks carry everything above (each field checked before it reaches `psm`), a `sni.check` task, and the join token travels in the environment (`PSM_AGENT_TOKEN`) instead of the command line, where any user could read it in the process list.
- `psm migrate export` encrypts the bundle with a passphrase by default — it holds every private key and password of the server; `--no-encrypt` writes a plain one, `--encrypt` is still accepted. The passphrase reaches openssl on a file descriptor instead of its environment, a push that fails removes the bundle it copied to the target, the SSH control socket lives in the run's own directory, `accept-new` host keys are asked for only where ssh knows the option, and a PSM installed at another path is rewritten without sed reading the old path as a pattern.
- From the 2026-09-26 code audit, the ones that could hurt: a hop rule's tag is no longer run through `eval` (a tag could run commands as root); a users store that stops parsing (a power cut, a full disk) is never read as empty — the periodic check used to write that back and every core restart then removed the accounts — and the last good copy is kept beside it; `psm user links` and `--show-secrets` are root's; a restore reports an archive that does not unpack instead of "restore complete", takes a quick backup first, restores quick backups too, and quick backups are rotated like full ones (the backup directory is root's alone); names typed into the site, certificate and SNI menus can no longer leave their directory (`../conf.d` meant `rm -rf /etc/nginx/conf.d`) or add Nginx directives, and an SNI entry cannot replace the `default` blackhole; the honeypot bans for 7 days, longer for repeats, never for good, puts the SSH client it was enabled from on the allow-list and inserts its rules ahead of ufw's and firewalld's chains, which used to drop the packet before it was logged; the firewall quick-lock keeps SSH on the port sshd really listens on, 80/443, every node, relay and port PSM opened, instead of resetting ufw to 22 and 443; `chattr +i` on resolv.conf no longer makes the next DNS change fail while reporting success; expiry dates, "+N months" and ping parse on BusyBox; the REALITY probe and `psm doctor` no longer end under `set -e` halfway; uninstalling removes psm-agent; a wildcard certificate is installed under the name it was issued for; a config Xray refuses is rolled back to the last one that started (sing-box and mihomo already were).
- And the rest of the audit: acme.sh is installed from a pinned release checked against its SHA-256 instead of `curl … | sh`; geoip/geosite are checked against their `.sha256sum`; `update`'s "update available" no longer counts fetch errors, and local edits are kept as a patch when the auto-update resets the scripts; Xray inbounds with a quote in their tag stay JSON; a cron drop-in and an OpenRC service file cannot be given a second line; `psm node` redacts VLESS Encryption keys, ShadowTLS passwords and mKCP seeds; traffic counters match a tag as text and the traffic state is written under a lock; `state_set`, `jq_set` and the stores write atomically next to the file and keep its mode; SSH hardening reloads rather than restarts sshd, removes the old port's rule after a confirmed change and needs jq for its rollback before it touches anything; fail2ban takes addresses and times only; the main menu's 9 opens the website menu; and a few dozen smaller ones (see `tests/integration/audit.sh`, which drives each finding the way it went wrong, on Debian, Alpine and Rocky).

- Self-signed TLS nodes work again from Xray clients (v2rayN, v2rayNG, Happ …), and every export now pins their certificate instead of skipping verification. Xray refuses `allowInsecure` outright since 2026-06-01 (v26.6.2 deleted the field) and current v2rayN no longer passes it on; it pins the certificate named in the link instead (`pcs`, Xray's share-link standard). PSM's links for such nodes carried only `allowInsecure=1`, so a VLESS, Trojan, VMess or Hysteria2 node that PSM signed itself (sing-box / mihomo without a domain) could not connect from any Xray-based client. The links now carry the certificate's SHA-256 next to the old flag — `pcs` in vless:// and trojan:// (also read by mihomo), `"pcs"` in vmess://, `pinSHA256` in hysteria2://, `hpkp` in anytls:// (mihomo) — so clients that know the pin check that one certificate and the others behave as before. `psm node export --format clash` adds `fingerprint` (mihomo checks it even with `skip-cert-verify` on, which stays for Stash), `--format singbox` writes `certificate_public_key_sha256` instead of `insecure` (sing-box 1.13+), and the menus' links and Clash snippets do the same. Measured with Xray v26.9.9, sing-box 1.14.2 and mihomo v1.19.31 as clients: every self-signed node connects pinned, a wrong pin is refused by all three, and the same link without `pcs` fails in Xray.
- Fixed Xray mKCP nodes that no client could connect to. Measured with real cores on both sides (Xray v25.12.8, v26.3.27 and v26.9.9 as client and server): the seed/header wire format is the same classic one in Xray v25's `kcpSettings.seed`, in v26.3.27's finalmask (`mkcp-aes128gcm` / `header-*`) and in v26.6's `mkcp-legacy` — which is what v2rayN 7.25 writes — but two things PSM did broke it. On Xray v26.9.9 (the preview channel) PSM preferred `kcpSettings.seed` because that core accepts it again, yet that form no longer interoperates with anything but itself: not with v2rayN, not with an older core. And before v26.6.22 Xray applied finalmask masks last to first, so on the stable v26.3.27 a node with a disguise header (srtp, utp, wechat-video) was written the wrong way round. PSM now asks the installed Xray which finalmask form it takes (`mkcp-legacy`, else `mkcp-aes128gcm`, else the old `kcpSettings` for an Xray without finalmask — v25 silently ignores the key, so a mask type that does not exist is tried first) and orders the masks for that release. `psm doctor` compares every mKCP inbound with what its node builds now and `psm doctor --fix` rewrites the ones an older PSM wrote.
- New Xray mKCP nodes get VLESS Encryption (X25519) by default. mKCP carries VLESS without TLS, and Xray clients from v26.7.7 on refuse VLESS without TLS or VLESS Encryption towards a public address ("vless without TLS or other encryption is prohibited"), so a plaintext mKCP node cannot be used from a current client. `--vless-enc none` (or answering no in the menu) keeps the old plaintext form for older clients.
- `psm node update … --vless-enc x25519|mlkem768|none` now does what it says: it makes the key pair, replaces it when the other kind is asked for, or removes it. Before, VLESS Encryption could only be chosen when a node was made; an update stored the option and changed nothing.
- Hysteria2: `--bbr-profile conservative|standard|aggressive` (and a question in the three add menus), the BBR congestion profile the server sends with — `bbr_profile` in sing-box 1.14, `bbr-profile` in mihomo 1.19.24, `finalmask.quicParams.bbrProfile` in Xray v26.4.13. Unset keeps the core's default (standard). An older core would refuse the field (sing-box) or ignore it without a word (Xray, mihomo), so PSM asks for the version that has it; Xray's stable release (v26.3.27) does not, its preview channel does.
- The Xray VPNGate exit writes its IPv4-only resolution as `sockopt.domainStrategy`: Xray v26.9.9 deprecates `freedom.domainStrategy` ("will be removed"). Both Xray releases PSM installs accept the new form without warnings.
- `psm node export --format clash` now covers Xray's XHTTP nodes too (XHTTP, WebSocket, gRPC, HTTPUpgrade as mihomo's `v2ray-http-upgrade`, HTTP/2 as XHTTP stream-one, and the REALITY layer), so the panel's Clash subscription can carry them as mihomo proxies rather than share links. mKCP has none (mihomo's VLESS has no mKCP).
- Fixed obfuscated Hysteria2 nodes not connecting from PSM's sing-box export: the outbound had no `obfs`, so the server dropped every packet. Nodes with VLESS Encryption are left out of the sing-box export (sing-box has no VLESS Encryption) instead of producing an outbound that cannot connect.
- Core versions: the offline fallbacks are sing-box v1.14.2 and mihomo v1.19.31. Every generated configuration is checked against Xray v26.3.27 and v26.9.9, sing-box 1.14.2 and 1.15.0-alpha.8 (the preview channel) and mihomo v1.19.31; `tests/core-validate.sh` can print what a core warns about (`SHOW_WARNINGS=1`), which is how the VPNGate deprecation above was found.

- Removing a server from the panel now takes its relays off the machine as well. The leaving plan listed the nodes and the standalone servers, so `psm agent remove` left realm's rules — and the accounting rules that go with them — behind on a machine the panel had forgotten. The plan carries the relays too, and psm-agent deletes each one; an agent too old to know the field ignores it and behaves as before. psm-agent 0.9.0.

- Fixed `psm relay probe` taking three seconds for every sample. It measured the connect with `curl telnet://`, which connects at once but then sits there until `--max-time` expires: ten samples cost 31 seconds, so a server with a couple of relays spent half of every minute probing. bash opens the connection itself now (`/dev/tcp`) and the shell exits as soon as it is up — the same measurement in 0.36 seconds. `timeout` still bounds a port that silently drops packets, and spawning that subshell puts a floor of roughly 5 ms under the reading, which matters only for a hop to 127.0.0.1.
- Fixed the panel's relay readings arriving every 90 seconds rather than every 60. A measurement rides the next sync, and the probe itself took 31 seconds (above), so the 60-second timer was always missed by the sync that should have carried it. With the probe fast again the readings land 60 seconds apart; psm-agent also shortens its wait when the next measurement is due sooner than the panel's idle interval, so the interval holds whatever that is set to.
- psm-agent passes `--mount-443` when the panel asks for a node on the shared 443 (`mount443` in the task). Sharing the port is not a node setting but how the node is created, and PSM refuses to move one onto or off it as an update, so the panel fixes it at creation and never sends it again.
- `psm relay probe [TAG] [--samples N] [--json]`: how a hop is doing — round trip, jitter, loss and the bytes the relay has carried. The round trip is measured with plain TCP connects to the landing side rather than with ping, because ICMP is filtered often enough on these networks that ping would report loss that is not there, and a relay carries TCP anyway, so a connect is what the traffic actually experiences. Jitter is the mean absolute difference between consecutive round trips over the burst. A relay whose landing side never answers reports `rtt_ms: null` and 100% loss instead of a made-up number. psm-agent runs this every 60 seconds and sends the readings with its sync, the way it already sends the traffic counters; the panel keeps 7 days of them for its charts.
- A relay is metered on the same `PSM_TRF` accounting chain the nodes use, by its listening port, under the tag `relay-<tag>` so it can never collide with a node's. The rules are put in place when the rule is applied and taken away when it is deleted — including the old port's rules when a relay's listening port changes, which would otherwise keep counting for a port it no longer listens on.
- Fixed a relay that cannot listen being reported as running. realm keeps going when a single endpoint fails to bind — it logs `[tcp]failed to bind 0.0.0.0:PORT: Address in use (os error 98)` and serves the others — so the service stays active, and PSM, which judged the result by exactly that, wrote the rule and told the panel it was applied while the relay could not accept a single connection. A port that no rule already uses is now checked for another listener before the rule is applied, and the port is checked again afterwards; either way the previous rules are put back and nothing changes. The same class of bug as the sing-box one below, except that here the service does not die at all, only one of its endpoints does.
- `psm relay add|update` take their settings as JSON as well (`--input -`, `--input FILE`, `--data '{…}'`), the way `psm node add` already did, so psm-agent can send a relay exactly as it sends a node; a command-line flag still wins over the same field in the JSON. psm-agent gained the `relay.add`, `relay.update`, `relay.delete` and `relay.list` tasks, checked by their own validator — a relay has no core and no protocol, so the node check does not apply to it — and installs realm on first use, the way it installs a missing core for a node.
- Fixed `psm relay update` never being able to turn UDP or the TLS hop **off** through `--input`/`--data`: jq's `//` stands in for `false` as well as for null, so `{"udp": false}` read as "this field was not given" and left the switch as it was, while `true` worked. A boolean is now read by whether its key is present at all. This is the path the panel uses to change a relay, so from the panel a switch could only ever be turned on; `psm relay add` was not affected, because there a missing field and `false` mean the same thing.
- `psm relay list|show|add|update|delete|install`: the realm relays without questions, so the PSM panel can manage them (the panel's 中转). The entry machine forwards a port to the landing machine, whose nodes do not change — realm works at L4 and neither parses nor decrypts what passes through. Only the entry machine needs a rule. The rules stay in `config/realm/rules.json`, the menu's own store, and realm's `config.toml` is generated from it as before, so a relay made from the menu and one made from the command line are the same thing.
- A relay's hop can be encrypted: `--tls` wraps the forwarded stream in TLS, so what travels between the two machines no longer looks like the node's own protocol. Which side a rule is follows from where it forwards: to this machine (127.0.0.1) it terminates TLS and holds the certificate (`--tls-cert`/`--tls-key`, else a self-signed pair made for `--tls-sni`), to another host it dials it (`--tls-sni`, with `--tls-insecure` to accept a self-signed one). Encryption is off by default and the menu's plain rules are untouched. realm writes this as `listen_transport` / `remote_transport`, measured on realm 2.9.4, which reports `transport=[tls][plain]` for such a rule.
- `realm_install_unattended` installs realm without questions, the way `psm core install --if-missing` installs a core: `psm relay add` and `psm relay install` fetch it when it is missing, so a server that never ran a relay needs no menu visit first.
- Fixed the Xray REALITY node the menus could not add: `reality.sh: line 374: server_names_raw: unbound variable`, and the script ended there (#4). The own-domain question defaults to no, and answering it leaves `server_names_raw` unassigned — `local x` declares a variable without setting it, so the camouflage branch that reads it next ends the script under `set -u`. It is initialised empty now. This came in with `fbfbeef`, which replaced the hardcoded public camouflage domain with "discover or type one", but kept the declaration as it was; the command line (`psm node add xray reality …`) was never affected, which is why the suites, all of which use it, did not catch it.
- `psm doctor` reports whether `/dev/net/tun` is there, with the kind of virtualisation the server runs under. Containers — LXC and OpenVZ especially — usually have no TUN device unless the host hands one out, and the free residential exit (VPNGate, over OpenVPN) cannot work without it; WARP can, since all three cores speak WireGuard themselves. The check is a warning, not a failure, and says to ask the host for TUN or to use the WARP exit instead. psm-agent already reports `psm doctor --json`, so the panel's diagnostics show it too, and the panel's exit field now says the same before a node is made.
- The menus can edit a node now: **修改节点（端口 / 密钥 / 域名）** / "Edit a node (port, keys, domain)", one entry in each core's menu (sing-box and mihomo item 15, Xray item 14). It lists that core's nodes whatever their protocol and changes one field — port, password, UUID, SNI, domain, REALITY's serverName, dest or short id, or the public port — through `_node_cli_cmd_update`, the same path the command line and the panel use. The protocols' own menus only ever offered a subset: AnyTLS could change its password but not its port, and Hysteria2, TUIC, VLESS and WireGuard on sing-box and mihomo offered nothing at all, so a node made in the menus could not be edited there. Pressing Enter leaves the field alone (an empty value would have written an empty password).
- Fixed a node with an exit registering WARP, or dialling the residential line, on a server whose core is not installed — and then failing with "sing-box did not take the WARP outbound", which named the wrong cause. `psm node add|update` checks that the core is there before it prepares the exit, so nothing is left behind for a node that cannot be made and the error says what is actually missing. Reported as "the panel cannot install AnyTLS with a WARP or residential exit"; on the panel's own path psm-agent installs the core first, so this hit the command line and any path where the core was missing.
- Fixed `psm node update … --server-name` leaving REALITY's camouflage domain unchanged in the core. The node store keeps `server_names_raw` (the raw comma-separated list) beside `server_name`, and Xray's inbound is written from `server_names_raw // server_name`; only the latter was updated, so the core kept serving the old domain while the node and its share link showed the new one. The raw list now follows a changed `server_name`, unless `--server-names-raw` is given (several SNIs).
- `psm --update <what>`: `scripts`, `xray`, `singbox`, `mihomo`, `hysteria2`, `nginx`, `geo` or `all`, without questions. `psm --update` alone still opens the menu; before, that was the only form, so psm-agent, the panel or cron calling it got the menu printed at a stdin that is not there, and a non-zero exit instead of an update.
- The menus can set a node's exit now: **节点出口分流（WARP / 家宽）** / "Per-node exit (WARP / residential)", one entry in each core's menu (sing-box and mihomo item 14, Xray item 13). It lists that core's nodes whatever their protocol, with the exit each one has, and sets or clears it — writing the same rule as `psm node add … --exit`, so a node set up from the menu, from the command line or from the panel is the same thing. Reported as "AnyTLS cannot use the residential exit": the command line and the panel could always do this for every protocol (measured here on sing-box, mihomo and Xray, with WARP and VPNGate), but no menu ever asked. The routing menu's own WARP and VPNGate entries write geosite rules for the whole server, not for one node, so from the menus there was no way to give a single node an exit. Nothing about it was specific to AnyTLS.
- Remote rule sets are written the one way sing-box 1.14 accepts without a deprecation: `http_client: {detour: ""}`. Measured by starting 1.14.1 on each form: `detour: "direct"` fails outright ("detour to an empty direct outbound makes no sense"), leaving the field out — or writing `http_client: {}` — warns that the implicit default HTTP client "will be removed in sing-box 1.16.0", and the legacy `download_detour` warns the same. Older sing-box keeps `download_detour`. PSM fetches rule sets to local files anyway; this covers the fallback when that download fails.
- Fixed sing-box 1.14 refusing to start — every node on the server down — as soon as a routing rule used a geosite or geoip set. PSM wrote each remote rule set with `http_client: {detour: "direct"}`, and 1.14 rejects a detour to its plain direct outbound ("detour to an empty direct outbound makes no sense"); the field is simply left out now (the default HTTP client is direct anyway). It hit the routing menu's geosite rules, its "unlock Netflix / OpenAI through WARP" preset and the new per-node exits alike.
- Rule sets are fetched by PSM when the rules are applied and referenced as local files (refreshed daily), instead of being downloaded by sing-box while it starts. A download that fails during startup takes the whole core with it — on a server that cannot reach GitHub, for good — so the core no longer depends on the network to come up. If the fetch fails, the remote rule set is written as before and sing-box tries again itself.
- Fixed a config sing-box cannot run staying in place: `sing-box check` only reads the config, and `systemctl restart` reports success even when the unit dies straight after and enters its restart loop, so PSM's rollback never fired (it had already dropped the backup). A change is now kept only if the service comes up and stays up; otherwise the previous config is restored, restarted, and the service log is shown.
- Fixed `psm node add` opening no firewall port on servers with an iptables firewall (and, by chance, with ufw). The check for an enforcing firewall piped `iptables -S` into `grep -q`; grep stops at the first match, which is the policy line, iptables could die of SIGPIPE while still writing, and under manager.sh's `set -o pipefail` the match then counted as a failure: no firewall found, no port opened. The firewall checks read the output first now, and an iptables rule that did not go in is reported instead of being taken as done. Found by the PSM panel's every-node test on Alpine.
- Fixed the sing-box subscription of a set of nodes that includes mihomo's VLESS over XHTTP: sing-box has no XHTTP transport, its outbound was written anyway, and sing-box refused the whole config. Such a node has no sing-box outbound now (it stays in the share links and the Clash profile).
- Exits for one node's traffic: `psm node add|update … --exit warp|vpngate [--exit-sites all|ai|streaming|GEOSITE,…] [--exit-country CC]` routes what comes in on that node — all of it, or only those sites (ai: OpenAI, Anthropic, Gemini; streaming: Netflix, Disney+, HBO, Prime Video, Spotify) — through Cloudflare WARP or the free residential line (VPNGate), in Xray, sing-box and mihomo alike; everything else goes out directly as before. The rule is tied to the node (`.node` in the core's routing store), so updating the node rewrites it, `--exit none` or deleting the node removes it. WARP is registered on first use; the residential tunnel is connected on first use (a residential or mobile line in CC, default JP; one per server, kept while it is up, with its watchdog on). The exit is set up before the node is made, so a line that does not answer leaves nothing half made. `psm exit status|warp|vpngate` shows and prepares them. For this, an inbound routing rule can carry `geosite` (Xray: inboundTag with domains; sing-box: inbound with rule sets; mihomo: `AND,((IN-NAME,…),(OR,(GEOSITE,…)))`).
- `psm sni find [--engine netlas|quake|zoomeye|fofa] [--key-stdin] [--json]`: the REALITY menu's search for camouflage targets in the server's own network, without questions — a cyberspace-mapping engine lists hosts in the same ASN with their certificate names, each is checked with a TLS handshake, the healthy ones come back by latency. The engine's key can come on stdin for that one search (it is not saved); without it the menu's saved key is used.
- psm-agent 0.5.0: the `sni.find` task (the engine's key travels on stdin only), and node changes run with the long timeout, since a node whose exit is the residential line connects it first. `lib/agent.sh` installs 0.5.0.
- Nodes made with `psm node add` (and so every node from the PSM panel) now work on a fresh server. A user found that on the panel many sing-box protocols would not install, and the ones that did could not be reached. Three causes, all fixed:
  - The TLS protocols of sing-box and mihomo (Hysteria2, TUIC, AnyTLS, VLESS + TLS, Trojan, VMess) and Xray's Hysteria2 required `cert_path` / `key_path`, so on a server without certificate files they were refused. Without them now, a node takes its SNI's certificate when PSM has one (`/etc/nginx/ssl/<domain>/`), else a self-signed one (SNI `www.bing.com` unless given), with `insecure = 1`, as the menus do. Certificate paths that do not exist are refused with that reason.
  - `psm node add` never opened the node's port; only the menus did. It opens it now in the enforcing firewall (ufw, firewalld or an iptables default-deny: UDP for Hysteria2 / TUIC / WireGuard / mKCP / QUIC, TCP and UDP for SS2022 / Snell / SOCKS). A rule PSM added is recorded (`config/firewall-ports`) and removed with the last node on that port, and on a port change; a port the firewall already allowed is left alone.
  - Self-signed VLESS and Trojan links lacked `allowInsecure=1`, the sing-box outbounds of VLESS / Trojan / VMess lacked `tls.insecure`, and mihomo's share-link import cannot skip verification for VLESS, VMess or TUIC at all. The links and outbounds carry it now, and `psm node export … --format clash` prints the TLS protocols as ready mihomo proxies (with `skip-cert-verify`), which psm-agent 0.4.1 sends to the panel for its Clash subscription.
  - Xray's domain protocols (Vision, XHTTP over TLS, Trojan, VMess) for a domain without a certificate are refused before anything changes, saying how to get one; before, Xray refused its whole config and every Xray node on the server went down.
  Covered by `tests/integration/panelside.sh` (behind an iptables default-deny: self-signed nodes made, their ports opened and shut again, a sing-box client through a self-signed Hysteria2 node) and by the panel's every-node test, which now runs each server behind ufw, firewalld or iptables with no certificates and connects from a separate client machine.
- Fixed deleting the last Xray SS2022 node leaving it running: PSM removed it from its list, but the rebuild returned early for an empty list, so the inbound stayed in Xray's live config and its port kept listening (deleting one of several was fine). Found by the PSM panel's every-node test (the panel deletes nodes through `psm node delete`); `tests/integration/panelside.sh` now checks that deleting one of two SS2022 nodes and then the last closes both ports and leaves no shadowsocks inbound.
- psm-agent 0.4.1: removing a server from the PSM panel now cleans up the server. The panel sends `agent.leave` with the nodes and standalone servers it made there; psm-agent deletes them (nodes made on the server's own command line are not in the list and stay, as do PSM and the cores), reports what it removed, and once the panel has that report runs `psm agent remove --yes` outside its own service (a transient systemd unit, or a new session under OpenRC, so stopping psm-agent does not stop the removal). - Added accounts on the nodes, for all three cores: `psm user add NAME [--nodes all|TAG,…] [--days N | --expires DATE] [--quota SIZE]`, with `list`, `show`, `update` (nodes, expiry, quota, `--reset-usage`, `--enable` / `--disable`), `delete`, `links` and `token`. Each user gets one UUID and one password, used on every node assigned to them (VLESS / VMess / TUIC take the UUID; Trojan / Hysteria2 / AnyTLS / TUIC / SOCKS the password), and their own subscription URL under the online subscription's domain, which `token` replaces (the old URL stops working at once). - Added VLESS Encryption (post-quantum ML-KEM-768 + X25519 key exchange) for Xray REALITY / Vision / XHTTP nodes and mihomo VLESS nodes, interactively or with `--vless-enc x25519|mlkem768`. X25519 authentication is the default because the ML-KEM-768 client key is about 1.6 KB. Enabled nodes drop `fallbacks`, which Xray refuses next to `decryption` even as an empty array. Verified end to end: a real client reaches the internet through the real server, and a client holding the wrong key does not.
- Added ShadowTLS v3 for mihomo SS2022 and Snell listeners (`--shadow-tls-sni`), with Clash and Surge snippets instead of a share link. The handshake target gets the same shared-CDN-frontend check as a REALITY dest, since ShadowTLS relays unauthenticated connections to it. Verified end to end with the exact client snippet PSM prints.

- Added subscribed rule sets for sing-box and mihomo (issue #3): paste a community rule-list URL, pick an exit, and the traffic it describes leaves through that exit. Both cores use their native path, so refreshing never restarts anything — mihomo gets a `rule-providers` entry it refreshes on its own interval, and sing-box gets a local `source` rule set, which it reloads by itself when the file changes (1.10+). Xray has no rule-set concept, so its rules are inlined into `config.json` instead, which is also the only core that has to be restarted when a list changes.
- Added `manager.sh --ruleset-update` and a daily timer that keeps the lists current. The refresh cost differs per core and the timer respects that: mihomo needs nothing (the core refreshes its own provider), sing-box only needs its rule-set file rewritten, and Xray is rebuilt and restarted — but only when the content actually changed and Xray really has that rule set bound, so a no-op fetch never drops anyone's connections. The timer carries a randomized delay of up to an hour, because every install pulling the same community repository at the same second is not a nice thing to do.
- Rule lists are parsed once in a shared layer rather than trusted blindly, and the preflight report is shown before anything is applied. Client-only types (`PROCESS-NAME`, `USER-AGENT`, …) and `IP-ASN`, which only mihomo understands, are counted and reported as dropped instead of being silently skipped — a rule set that half-applies is the worst kind to debug. Malformed entries are filtered out too, since one bad line makes a core reject the whole config.
- Both generated forms deliberately split domains and IPs into separate rules. In sing-box a rule's fields are ANDed, so `domain` and `ip_cidr` written into one headless rule would mean "domain AND IP", which never matches; `domain`, `domain_suffix` and `domain_keyword` share one matcher and are ORed, so those do belong together. The same trap applies to Xray and is what the second step has to get right.
- Rule sets are capped at 5000 rules, and the reason is stated in the UI: a full routing table belongs on the client, where domestic traffic is decided before it ever crosses to the VPS, and mihomo matches `classical` rules linearly, which costs CPU under load. Server-side rule sets are for choosing the exit — OpenAI, Netflix and the like.
- Updating compares the rule count against the stored one first and refuses a change that shrinks by more than half or grows more than fivefold. Injecting a third-party URL into routing hands the "which traffic leaves where" decision to whoever maintains that repository, so a wild swing is treated as a signal to stop and ask rather than something to apply. Only https URLs are accepted.

- Fixed Xray and sing-box installs failing outright: the download URL came out as `.../download/[step] Fetching the latest version...\nv26.3.27/Xray-linux-64.zip`. The version resolvers return the tag on stdout while also reporting progress with `log_step`, and `log_info`/`log_warn`/`log_step`/`log_ok` all wrote to stdout, so `tag=$(_xray_resolve_tag ...)` swallowed the log line along with the tag. All log helpers now write to stderr, the way `log_error` already did — logs are diagnostics, not return values, so this removes the whole class of bug rather than patching the two call sites. mihomo was never affected: it resolves its tag inline instead of through a command substitution.
- Fixed the Telegram bind token being generated empty, which silently disabled the check it was supposed to enforce. `tr -dc 'A-Za-z0-9' < /dev/urandom` exits with "Illegal byte sequence" in a UTF-8 locale unless `LC_ALL=C` is set, and the generator was missing it, so `/token <port>` could store an empty token — while the bind path treats an empty stored token as "no token required" and lets anyone bind to that port. The generator now reuses the hardened `rand_str`, an empty token is refused instead of stored, and the failure is reported rather than passing silently.
- Hardened `rand_str`, which produces every password, PSK and camouflage path in the project: it now verifies it actually got the requested length, falls back to `od` plus bash string operations (deliberately not `tr`, which is what failed above), and errors out instead of returning an empty string, so a node can never be created with an empty password.
- Fixed two `set -o pipefail` hazards where `head` exiting early leaves the upstream process with SIGPIPE and the pipeline returning 141: the Telegram token generator (measured non-zero 20 times out of 20, which aborted the bot daemon through a bare assignment under `set -e`) and the nginx dynamic-module lookup.
- Added a VPNGate residential-IP exit, shared by Xray, sing-box, and mihomo. It fetches the public VPNGate server list, classifies each candidate IP through ip-api's batch endpoint, and keeps the ones that are actually home broadband — datacenter nodes and VPNGate's own relays at `219.100.37.x` are demoted, because those are hosted, widely known, and already blocked by the services people want to unlock. The `proxy` flag is deliberately not used for that verdict (nearly every VPNGate node is in public proxy databases, so it would reject the entire list); it is shown as a risk hint instead. Candidates are tried in order until one connects and its exit IP can actually be probed. The exit country is always chosen by the operator from a numbered list of the countries that actually have nodes (with their node counts) rather than defaulted to, since the exit country is what decides which catalogue a streaming service shows.
- The residential tunnel is an openvpn client on its own `psmvg0` device with `--route-nopull`, writing only into a dedicated routing table: the main table is never touched, so SSH and every existing node keep using the datacenter link. Cores reach it by marking connections (`sockopt.mark` on Xray, `routing_mark` on sing-box, `routing-mark` on mihomo) — not by binding to the interface, which needs `CAP_NET_RAW` that none of the three systemd units carry, while `SO_MARK` only needs the `CAP_NET_ADMIN` they already have. Because the outbound refers to a mark rather than a node, rotating to a different residential IP never rewrites any core config. When the tunnel is down the table keeps only a blackhole route, so matched traffic fails closed instead of leaking back out through the datacenter IP.
- Failover is automatic and stays inside the chosen country. VPNGate nodes are volunteers' own machines that can be powered off, renumbered, or unplugged at any moment, so a watchdog probes the tunnel every two minutes and, after two consecutive failures, moves to another node **in the same country** — drifting to a different country would silently change which regional catalogue the unlock rules reach. The dead node is put on a six-hour cooldown so rotation does not keep landing back on it, and when every same-country candidate is exhausted the list for that country is refetched before giving up. OpenVPN is also given `ping`/`ping-restart`, because a peer that loses power never sends a FIN and would otherwise leave the tunnel hanging.
- VPNGate nodes still run AES-128-CBC with SHA-1 certificates, which OpenSSL 3 refuses by default, so generated configs relax `tls-cipher` and `data-ciphers` — but only on OpenVPN 2.5+, since those options do not exist on the 2.4 that ships with Debian 10 / Ubuntu 20.04. A first failure that looks like a legacy-algorithm rejection is retried once with `providers legacy default`. Compression directives from the official config are kept as-is: they describe the framing the far end expects, so dropping them breaks the tunnel.

- Removed the shipped Reality camouflage defaults (`www.cloudflare.com` for Xray/sing-box/mihomo Reality, `www.microsoft.com` for XHTTP reality-layer) on every server-side path, interactive and `psm node` alike. Cloudflare's own domain is the exact case the Xray docs warn about, and any hardcoded well-known domain can move behind a CDN later without the script noticing — while everyone sharing one default is itself a fingerprint. Xray now defaults to mapping-engine discovery, which finds same-ASN targets and so naturally avoids both CDN frontends and large content-distribution sources, matching upstream's "steal a certificate from your own ASN" best practice. sing-box and mihomo have no discovery path, so they require an explicit target instead. The non-interactive CLI fails with a clear message rather than silently building a node on a borrowed default. Client-side outbound SNI prompts are unchanged — they are not affected by this.

- Hardened the Nginx 443 SNI multiplexer against being used as a free relay. Unknown SNI used to fall through to the Reality inbound, and REALITY forwards every connection that fails authentication straight to its `dest` — so anyone who could reach port 443 made the server pay for a round trip to `dest`. When `dest` sits on a multi-tenant CDN frontend, an attacker only had to put an arbitrary CDN-hosted hostname in the ClientHello to get a free tunnel into that entire CDN. Unknown SNI is now dropped without opening any upstream connection, and existing installs are migrated on the next Nginx sync. Mounted nodes are unaffected: each one already has an explicit SNI entry, and a prober using the node's real serverName still gets the full genuine REALITY fallback.
- Added multi-tenant CDN frontend detection for Reality camouflage targets across Xray, sing-box, and mihomo. The check probes the target's IP with unrelated SNIs and flags it when a valid certificate comes back for a hostname the target does not own — testing the property that actually matters (does this IP serve arbitrary tenants?) rather than tracking CDN IP ranges or ASNs. It warns rather than blocks, since the verdict can misfire and the risk is the operator's to weigh.
- Added REALITY fallback rate limiting (`limitFallback*` on Xray, `limit-fallback-*` on mihomo) for nodes whose target was flagged as a shared CDN frontend. It only touches connections that fail REALITY authentication; authenticated clients are unaffected. This is a backstop, not a fix: both parameters are per-connection, so an abuser who reconnects in a loop bypasses them. sing-box has no equivalent option, so nodes on it are warned when a flagged target is combined with direct-listen mode, which leaves no protection layer at all.
- Documented the CDN-fronted `dest` problem in all four READMEs, which so far only existed in this changelog and in code comments. There is now a FAQ entry explaining why REALITY's unconditional fallback turns a CDN-fronted `dest` into a free port forwarder, what the three layers of defence are, and where they do not hold (per-connection `limitFallback`, and sing-box direct-listen having no backstop at all). The 443 port-reuse diagram was also stale: it still showed unmatched SNI falling through to the decoy site, which stopped being true when unknown SNI became a blackhole.

The installer now warns about this when the preview channel is chosen, and the Reality menu lets you relax the threshold per node. Leaving it unset writes no field at all, so older Xray builds are unaffected.
